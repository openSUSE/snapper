Btrfs Rollback Methods
======================

Snapper supports two mechanisms for switching the active root subvolume
during a rollback. The mechanism is selected by the ambit (see the
--ambit option in snapper(8)); with the default of auto it is detected
from the system.


classic and transactional (set-default)
---------------------------------------

Sets the btrfs default subvolume ID via BTRFS_IOC_DEFAULT_SUBVOL. This
works when the bootloader or fstab does not specify a subvol= mount
option and instead relies on the btrfs default subvolume.

This is the traditional snapper rollback behavior.


subvol-rename
-------------

Atomically swaps the named root subvolume using renameat2(2) with
RENAME_EXCHANGE. This is required when fstab (or the bootloader) mounts
the root filesystem with an explicit subvol= option such as subvol=@root,
because in that case the btrfs default subvolume ID is ignored.

The sequence is:

  1. A read-write copy of the rollback target snapshot is created as
     <subvol>.incoming (e.g. @root.incoming).

  2. renameat2(RENAME_EXCHANGE) atomically swaps <subvol>.incoming with
     the current root subvolume (e.g. @root). There is no point in time
     where @root does not exist.

  3. Subvolumes nested in the root subvolume are handled, see below.

  4. The displaced root is moved to <subvol>.rollback.<N>, preserving
     the old root for recovery. With ROLLBACK_BACKUP_LIMIT set, the
     oldest of these backups beyond the limit are deleted.

Renaming a mounted btrfs subvolume is safe: the kernel tracks mounts by
subvolume ID, not by name, so the running system is unaffected. Requires
Linux 3.17 or later for renameat2(RENAME_EXCHANGE) support.

The read-write copy that becomes the root is not added to the snapshot
qgroup (QGROUP), like the new default in a classic rollback: only
snapshots with a cleanup algorithm belong there.


Nested subvolumes
-----------------

A btrfs snapshot does not include subvolumes nested in the snapshotted
subvolume. Where one was, the snapshot only holds a placeholder: an
empty directory in which nothing can be created until it is removed.
So after the exchange the nested subvolumes are still in the old root,
and the new root has placeholders at their paths. They are handled by
this rule:

  .snapshots  moved into the new root, and mounted again by subvolume ID
              on the running system so snapper keeps working until the
              reboot

  empty       the placeholder is removed from the new root, so the path
              can be recreated, e.g. var/lib/portables and
              var/lib/machines by systemd-tmpfiles at boot; the empty
              subvolume stays in the old root

  not empty   the rollback is refused before anything is changed, since
              the data would only be reachable in the old root; such
              subvolumes should be top-level subvolumes mounted via fstab
              (like /home), or be emptied

Layouts that keep these subvolumes outside the root subvolume, e.g. with
a separate /var subvolume, only have .snapshots nested in the root.

The same applies to a classic rollback, where the new default subvolume
is a snapshot too; it is not handled there.


Plugins
-------

The subvol-rename ambit runs the same plugins as a classic rollback.
set-default-snapshot-pre and set-default-snapshot-post are run around
the exchange with the number of the snapshot whose copy becomes the
root, i.e. the snapshot booted next, although the btrfs default
subvolume is not changed. rollback-pre and rollback-post get the numbers
of the backup snapshot and of the new snapshot, as for classic.


Limitations
-----------

On many named-subvolume layouts /boot (or the EFI system partition
holding the kernel images) is not part of the root subvolume, so a
rollback does not change the installed kernels. After a rollback past a
kernel update the boot loader may start a kernel whose modules are
missing in the new root (/usr/lib/modules/<version>). A rollback-post
plugin can adjust the boot entries.


auto (default)
--------------

Snapper inspects the system to determine the ambit:

- If the system boots a top-level named subvolume (a single path
  component such as "@root"), subvol-rename is used. The name comes from
  the boot configuration: rootflags=subvol= on the kernel command line,
  which decides at boot, or, for a one-off boot of a snapshot (by
  subvolid= or a nested name), subvol= of the / entry in /etc/fstab, which
  describes the normal boot. /proc/mounts is not used for this: it shows
  the running root under its current name, which after a rollback without
  a reboot is <subvol>.rollback.<N>.
- Otherwise, when booting by the btrfs default subvolume id, the ambit is
  classic or transactional, depending on the read-only/-write state of
  the default subvolume, and set-default is used.
- The rollback is refused when neither method changes what boots: the
  root pinned by subvolid=, mounted by a nested name, or the kernel
  command line and fstab naming different subvolumes. A subvolid= next
  to subvol= in fstab (as older genfstab versions write it) is reported,
  since it no longer matches after the rename.
- subvol-rename requires snapper built with libbtrfsutil.

An explicit --ambit always wins over the detection. This means no manual
configuration is needed on most systems.
